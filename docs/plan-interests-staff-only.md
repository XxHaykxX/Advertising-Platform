# План — заявки бренда живут только у сотрудников

**Статус:** утверждён владельцем 11.08.2026. Формулировка владельца: «заявки от бренда
идут только в staff; потом решим, кому передавать, но только внутри staff».

**Правило.** Заявка бренда — внутренний лид платформы. Её видит, ведёт и отвечает на неё
сотрудник (`SUPERADMIN` / `MODERATOR`) в `/admin/interests`. Создатель проекта не получает
ни уведомления, ни контактов бренда, ни кнопок «принять / отклонить». Кому лид передадут
дальше — решение внутри staff, и оно принимается **позже**; до тех пор адресат один —
очередь сотрудников.

---

## Что уже соответствует правилу (решение 2026-08-07, живёт на проде)

Проверено по коду и по прод-базе 11.08:

- `submitApplication` (`src/app/account/brand/actions.ts:361`) шлёт уведомление только
  через `notifyRoles(["SUPERADMIN","MODERATOR"])` со ссылкой `/admin/interests`.
- `respondToInterest` (`src/lib/actions/interest-response.ts`) пускает к ответу только
  staff-сессию с `canHandleInterests`. Создатель убран из цепочки целиком.
- `/account/interests` — заглушка-редирект на `/account/notifications`, страницы-инбокса
  у создателя больше нет.
- В прод-базе 10 уведомлений `INTEREST` ведут на `/admin/interests`.

То есть костяк правила стоит. Ниже — то, что ему **не** соответствует.

---

## Этап S1 — сотрудник узнаёт о заявке письмом, а не только колокольчиком

Сейчас новая заявка порождает только запись в инбоксе и web-push. Почта уже настроена и
работает (`src/lib/mail.ts`, SMTP в env; письма о модерации и об ответе бренду уходят), но
для самой заявки письма нет. Переговоры ведёт staff — значит, пропущенный лид ничей.

- `newInterestForStaffTemplate` + `notifyNewInterestToStaff` в `src/lib/mail.ts` рядом с
  `newProjectForModerationTemplate` — тот же адресат (`resolveAdminEmail()`), тот же
  «best-effort, ошибка не роняет действие».
- Вызов — в том же `try` блоке `submitApplication`, что и `notifyRoles`.
- В письме: проект, бренд, что именно куплено (плейсмент или пакет), ссылка на
  `/admin/interests`. Контакты бренда — ссылкой в админку, не текстом в письме.
- Проверка: заявка на проде → письмо на ящик администратора; SMTP выключен локально →
  предупреждение в лог, действие не падает.

## Этап S2 — убрать хвост старого маршрута

- В прод-базе два уведомления `INTEREST` ещё ведут на `/account/interests`. Пока они
  живы, заглушка-редирект обязана стоять.
- Миграция данных: переписать `link` этих строк на `/admin/interests`, если получатель —
  staff, и на `/account/notifications`, если получатель — участник.
- После миграции удалить `src/app/account/interests/page.tsx`: маршрут, у которого не
  осталось ни одной входящей ссылки, — мёртвый код, который читается как «тут когда-то
  был инбокс».
- Проверка: `SELECT COUNT(*) FROM Notification WHERE link='/account/interests'` → 0.

## Этап S3 — бренду сказать, кто ответит

`apply.success` — «Предложение отправлено», и всё. Бренд, отправивший заявку, не знает,
кто и в какой срок ответит, и ждёт создателя, которого в цепочке нет.

- Расширить текст: заявку принимает команда iGovazd, ответ придёт в кабинет и на почту.
- Три языка, `npm run i18n:keys`, подпись раздела в `i18n-csv.ts` (guard-тест уронит
  сборку на ключе без подписи).
- Заодно проверить тексты в кабинете бренда (`/account/brand/interests`): статусы
  «Отправлено / Взаимный интерес / Отклонено» не должны называть отвечающего создателем.

## Этап S4 — тест-сторож на границу

Самый повторяемый баг проекта — «страница есть, а тот, для кого она, её не видит», и
зеркальный ему «убрали из UI, но не из данных». Правило staff-only должно держаться
тестом, а не памятью.

- `src/lib/auth/interests-access.test.ts`: создатель не достаёт заявки ни маршрутом
  (`/account/interests` → редирект), ни экшеном (`respondToInterest` под member-сессией →
  `errNotAllowed`), ни слоем данных (в DTO кабинета создателя нет полей заявки).
- Проверка: тест краснеет, если `loadResponder` снова начнёт пускать участника.

## Этап S5 — seam для «потом решим кому» (не строим сейчас)

Решение о передаче лида откладывается, но очередь без адресата растёт. Чтобы не
переделывать потом всё:

- Зафиксировать, что маршрутизация — это одно поле `Interest.assigneeId` (nullable, FK на
  staff-пользователя) плюс фильтр «мои / ничьи» в `/admin/interests`. Ни в коем случае не
  новая сущность и не отдельная таблица маршрутов.
- Ничего из этого не пишем, пока владелец не скажет, по какому признаку делить.

## Заявки на рекламные места (этап 4 мультиканального плана)

Этап отложен (на проде ноль `AdSpace`), но правило распространяется на него **по
построению**: `submitAdSpaceApplication` уведомляет `notifyRoles(["SUPERADMIN","MODERATOR"])`,
владелец места не получает ни строки; отвечает staff тем же `respondToInterest`. Записать
это в `docs/plan-multichannel-ads.md` при возврате к этапу 4, чтобы инбокс создателя не
завёлся заново.

## Проверка

На каждом этапе: `npx tsc --noEmit`, `npx vitest run`, `npm run lint`, `npx next build`
(на Windows именно `npx` — `npm run build` врёт нулевым кодом выхода).

Функционально, на проде после деплоя:

1. Бренд подаёт заявку → в `/admin/interests` появилась строка, у сотрудника письмо,
   у создателя проекта — ни уведомления, ни письма, ни строки в кабинете.
2. Сотрудник отвечает → бренд видит статус в своём кабинете и получает письмо.
3. Старые уведомления из колокольчика открываются, а не ведут в редирект.

Порядок деплоя: миграция данных S2 катится **до** удаления заглушки, иначе клик по
старому уведомлению даст 404 (`docs/DEPLOY-PLAYBOOK.md`).
