# План — заявки бренда живут только у сотрудников

**Статус:** утверждён владельцем 11.08.2026. Формулировка владельца: «заявки от бренда
идут только в staff; потом решим, кому передавать, но только внутри staff».

**Правило.** Заявка бренда — внутренний лид платформы. Её видит, ведёт и отвечает на неё
сотрудник (`SUPERADMIN` / `MODERATOR`) в `/admin/interests`. Создатель проекта не получает
ни уведомления, ни контактов бренда, ни кнопок «принять / отклонить». Кому лид передадут
дальше — решение внутри staff, и оно принимается **позже**; до тех пор адресат один —
очередь сотрудников.

---

## Что уже соответствует правилу (решение 2026-08-07, живёт на проде)

Проверено по коду и по прод-базе 11.08:

- `submitApplication` (`src/app/account/brand/actions.ts:361`) шлёт уведомление только
  через `notifyRoles(["SUPERADMIN","MODERATOR"])` со ссылкой `/admin/interests`.
- `respondToInterest` (`src/lib/actions/interest-response.ts`) пускает к ответу только
  staff-сессию с `canHandleInterests`. Создатель убран из цепочки целиком.
- `/account/interests` — заглушка-редирект на `/account/notifications`, страницы-инбокса
  у создателя больше нет.
- В прод-базе 10 уведомлений `INTEREST` ведут на `/admin/interests`.

То есть костяк правила стоит. Ниже — то, что ему **не** соответствует.

## Этап S1 — сотрудник узнаёт о заявке письмом ✅ сделано 11.08

Сейчас новая заявка порождает только запись в инбоксе и web-push. Почта уже настроена и
работает (`src/lib/mail.ts`, SMTP в env; письма о модерации и об ответе бренду уходят), но
для самой заявки письма нет. Переговоры ведёт staff — значит, пропущенный лид ничей.

- ~~`newInterestForStaffTemplate` + `notifyNewInterestToStaff`~~ — стоят в `src/lib/mail.ts`
  рядом с `newProjectForModerationTemplate`: тот же `resolveAdminEmail()`, тот же
  best-effort (мёртвый SMTP не роняет отправку заявки).
- ~~Вызов в `submitApplication`~~ — в том же `try`, что и `notifyRoles`; название позиции
  берётся в дефолтной локали, письмо трёхъязычное.
- Контакты бренда в письмо намеренно не попали: письмо говорит «лид есть» и ведёт в
  панель, где эти данные и так на экране.
- Тест `src/lib/mail.interest.test.ts`: ссылка ведёт в staff-инбокс и никогда в старый
  инбокс создателя, имя позиции подставляется с фолбэком пакет→плейсмент, заявка без
  позиции не даёт «undefined», имя бренда экранируется.

## Этап S4 — тест-сторож на границу ✅ сделано 11.08

Самый повторяемый баг проекта — «страница есть, а тот, для кого она, её не видит», и
зеркальный ему «убрали из UI, но не из данных». Правило staff-only должно держаться
тестом, а не памятью.

- `src/lib/auth/interests-access.test.ts` — восемь проверок: экшен отказывает
  member-сессии и ролям `PUBLISHER`/`TRANSLATOR` **до** чтения заявки,
  `SUPERADMIN`/`MODERATOR` проходят гейт; маршрута `/account/interests` больше нет и на
  него никто не ссылается (href / redirect / `link:`); в `src/lib/data/interests.ts` нет
  экспорта `*ForOwner`, и ничего из `src/app/account` этот модуль не импортирует.
- Проверено мутацией: снял проверку роли в `loadResponder` — тест покраснел на
  `PUBLISHER`, вернул код обратно. Сканер импортов подпёрт позитивной проверкой
  (админка модуль импортирует), иначе он бы «проходил» после переименования.

## Проверка

На каждом этапе: `npx tsc --noEmit`, `npx vitest run`, `npm run lint`, `npx next build`
(на Windows именно `npx` — `npm run build` врёт нулевым кодом выхода).

Функционально, на проде после деплоя:

1. Бренд подаёт заявку → в `/admin/interests` появилась строка, у сотрудника письмо,
   у создателя проекта — ни уведомления, ни письма, ни строки в кабинете.
2. Сотрудник отвечает → бренд видит статус в своём кабинете и получает письмо.
3. Старые уведомления из колокольчика открываются, а не ведут в редирект.

Порядок деплоя: миграция данных S2 катится **до** удаления заглушки, иначе клик по
старому уведомлению даст 404 (`docs/DEPLOY-PLAYBOOK.md`).
