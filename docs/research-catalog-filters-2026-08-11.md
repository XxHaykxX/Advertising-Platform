# Research: фильтры `/catalog` против того, что мы продаём

Дата: 11.08.2026. Доклад, не проект решения — по решению владельца ничего не проектируем,
пока не прочитан этот разбор. Данные сняты чтением прод-базы, код — `src/app/catalog/`
(страница с тех пор переехала под `/ads` и фасеты стали реестром — см. пометку ниже и
`docs/ad-channel-filters.md`).

> **Обновление 14.08.2026.** `/catalog` слился с `/ads` (редиректом), а фасеты
> переехали из `catalog-view.tsx` (файла больше нет) в реестр `src/lib/catalog/facets.ts` —
> §3.2 «дефицит осей» отчасти закрыт: атрибуты канала (`src/lib/ad-channel-attrs.ts`)
> теперь генерируют чекбокс-фасет автоматически. Диапазоны, карта, аудитория и категория
> товара из §3.3 остаются открытыми. Актуальное описание механизма — `docs/ad-channel-filters.md`.
> Остальной разбор ниже не переписан — читать как снимок 11.08.

## Короткий ответ

Фильтр не «сломан» — он показывает ровно то, подо что есть данные, а данных нет.
Из девяти каналов в каталоге физически представлены два, и оба стоят у всех девяти
живых проектов сразу, поэтому фасет «Канал» ничего не отсеивает. Всё остальное, что
предлагает рейка, описывает **фильм** (жанр, формат, платформа), а не **рекламное
предложение** (цена, гео, сроки, охват). Бренду, который пришёл покупать рекламу,
фильтровать нечем.

## 1. Что рейка умеет по коду

`src/app/catalog/catalog-view.tsx`. Семь фасетов, все — чекбоксы, всё считается на
клиенте (весь каталог сериализуется в браузер, см. пометку `ponytail:` в файле):

| Фасет | Источник | Правило показа |
|---|---|---|
| Канал | `AD_CHANNELS` ∩ то, что есть в каталоге | только присутствующие коды |
| Жанр | `Project.genres` | только присутствующие |
| Формат | `Project.formatCategory` | только присутствующие + корзина «не указан» |
| Платформа | `Project.platforms` | только присутствующие |
| Вид интеграции | `Placement.placementType` | только присутствующие |
| Город | `AdSpace.city` | только присутствующие |
| Поиск | строка: название, жанр, страны, синопсис / адрес, размер, канал | всегда |

Плюс сортировка (по умолчанию / новизна / дедлайн / название) и переключатель
сетка-список. Правило «нет данных — нет фасета» соблюдается везде и намеренно: пустой
заголовок, открывающийся в никуда, уже ловили в QA.

Отдельная механика, которую важно знать заранее: **фасет одного вида неявно скрывает
другой вид**. Выбрал жанр — из выдачи исчезли все рекламные места (у них жанра быть не
может), выбрал город — исчезли все проекты. Сегодня это незаметно (мест ноль), но как
только появится наружная реклама, «Комедия» будет молча выкидывать билборды.

## 2. Что на проде (11.08.2026)

| Показатель | Значение |
|---|---|
| `AdSpace` — всех записей | **0** |
| Живых проектов (`APPROVED` + `isActive`) | 9 |
| Из них с плейсментами / с пакетами | 9 / 9 |
| Плейсментов с проставленным `placementType` | **0** из 14 |
| Пакетов с ценой | 5 из 22 (4 — на тестовом проекте) |
| Жанров в данных | 13 |
| Форматов | 2 (`FEATURE_FILM`, `SERIES`) |
| Платформ | 5 (Kinodaran, Cinema, YouTube, Armenia TV, Public TV) |
| Стран | 2 (Armenia, Georgia) |

Отсюда всё и следует:

1. Семь каналов из девяти (`VIDEO`, `RADIO`, `TV`, `BANNER`, `BILLBOARD`, `LIFTS`,
   `TRANSIT`) в фасете **не появляются** — под ними ноль записей.
2. Остаются `PLACEMENT` и `EVENTS`, но они выводятся из проекта: «есть плейсменты» →
   `PLACEMENT`, «есть пакеты» → `EVENTS`. У всех девяти проектов есть и то, и другое,
   поэтому **любой выбор канала даёт те же девять карточек**. Фасет декоративный.
3. Фасет «Вид интеграции» не рендерится вообще — ни один плейсмент не классифицирован.
4. Фасет «Город» не рендерится — он читает только `AdSpace`.

Итого бренд видит рейку из четырёх кино-фильтров и канал, который ни на что не влияет.
Отсюда и ощущение «фильтр только по placement».

## 3. Чего не хватает — три разных дефицита

Их важно не смешивать: лечатся они по-разному.

### 3.1 Дефицит данных (лечится контентом, код не трогаем)

- Ноль рекламных мест. Форма их заведения готова и открыта создателям
  (`/account/ad-spaces/new`, все семь каналов), но ей никто не пользовался.
- Ноль классифицированных плейсментов (`placementType`).
- 17 из 22 пакетов и 9 из 14 плейсментов без цены (подробности —
  `docs/offer-gaps-2026-08-11.md`).

### 3.2 Дефицит осей (поле в БД есть, фасета нет)

| Ось | Где лежит | Почему фасета нет |
|---|---|---|
| Цена / бюджет | `Placement.priceAmd`, `SponsorshipTier.priceAmd`, `AdSpaceOffer.priceAmd` | нужен диапазон, а рейка умеет только чекбоксы; плюс у 77% пакетов цены нет — фильтр по цене выкинул бы почти весь каталог |
| Период доступности | `AdSpace.availableFrom/To` | нет контрола дат |
| Дедлайн заявок | `Project.applicationDeadline` | есть только как сортировка, не как фильтр («успею подать») |
| Охват в сутки | `AdSpace.reachPerDay` | нужен слайдер-диапазон |
| Свободные слоты | `availableSlots` у всех трёх видов позиций | нет фасета «только с местами» |
| Эксклюзивность | `SponsorshipTier.isExclusive` | нет фасета |
| Стороны / размер | `AdSpace.sides`, `sizeFormat` | `sizeFormat` — свободный текст, закрытым списком не станет без нормализации |

### 3.3 Дефицит модели (поля нет вообще)

- **География проекта.** У проекта есть только страна производства. «Реклама, которую
  увидят в Ереване» отфильтровать нельзя: город есть лишь у рекламных мест.
- **Категория товара / индустрия.** `BRAND_CATEGORIES` живёт в профиле бренда, но
  предложение не говорит, каким категориям оно подходит (и каким запрещено — алкоголь,
  азартные игры). Это самый частый первый вопрос покупателя.
- **Аудитория.** Ни пола, ни возраста, ни соцдема ни у проекта, ни у места. `ageRating`
  — про контент, не про аудиторию.
- **Единый тип «предложение».** Цена/слоты/сроки лежат в трёх разных таблицах
  (`Placement`, `SponsorshipTier`, `AdSpaceOffer`) с разными колонками. Любой сквозной
  фильтр по цене придётся собирать вручную по трём источникам.
- **Ссылка на отфильтрованный каталог.** Состояние живёт в `sessionStorage`, в URL
  попадает только `?channel=`. Поделиться подборкой или дать её в рассылке нельзя.

## 4. Как это устроено на рынке

**Наружка и медиа — [AdQuick](https://www.adquick.com/marketplace)** (1,6 млн площадок,
1700+ владельцев). Фильтры: гео (город, индекс, радиус от адреса, DMA, близость к POI),
формат (статика, цифра, транзит, мобильные), **диапазон цены**, **объём показов
(impressions)**, аудитория, дейпарт, доступность в реальном времени. Карта — первичный
интерфейс, а не список: у наружной рекламы главный вопрос «где», и он пространственный.
Ср. с нами: гео есть только текстом в `city`/`address`, карты нет, показов нет как оси.

**Продакт-плейсмент — [Filmustage](https://filmustage.com/blog/product-placement-in-film-how-it-works-and-how-to-get-it-2026/),
[Placed](https://placedinfilm.com/), [BENlabs](https://www.benlabs.com/products/product-placement/).**
Здесь ищут по жанру и тону проекта, **типу бренда/продукта**, **бюджетному тиру** и
стадии продакшена. Порядок цен на рынке: product loan / gifting — $0, микро-плейсмент у
креатора — $100–500, заметный реквизит в стриминговом сериале — около $50 000. То есть
бюджетный тир — рабочая ось, потому что разброс на два порядка.

Общий вывод по обоим сегментам: **везде фильтруют по свойствам сделки — гео, цена,
объём аудитории, сроки.** Свойства контента (жанр) — вторичная ось, и только там, где
продают интеграцию в контент.

## 6. Что из этого следует (решение — за владельцем)

Три независимые развилки, ни одна не начата:

1. **Наполнение против переделки.** Если завтра завести двадцать рекламных мест с
   городом и ценой, фасеты «Канал» и «Город» оживут без единой строки кода. Ни одна из
   недостающих осей из §3.3 от этого не появится.
2. **Оси сделки.** Цена, гео проекта, сроки, категория товара — это новые поля и новые
   типы контролов (диапазон, даты, карта), а не ещё один список чекбоксов.
3. **Два вида в одной выдаче.** Сейчас фильтр одного вида молча прячет другой. С
   реальным инвентарём это станет заметно, и вопрос «каталог — один список или два
   раздела» придётся решить до того, как места появятся, а не после.
