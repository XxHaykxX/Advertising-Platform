# Аудит производительности — 2026-07-31

Замеры сняты с прода (igovazd.am) через headless Chromium, код разбирали параллельно
четыре агента (бандл, серверные запросы, медиа) плюс живые замеры. Ниже — что нашли,
что чиним и что владелец решил не трогать.

## Короткий вывод

**Сервер не тормозит.** TTFB на проде 140–220 мс, upstream по данным CDN 27–46 мс,
Prisma-кэш (`unstable_cache`, 300 с) работает. Чинить на серверной стороне почти нечего.

**Тормозит клиент.** На каждой странице ~936 КБ несжатого JS и картинки, которые
отдаются в исходном размере. Страница проекта — 1.4 МБ, каталог — 1.7 МБ.

## Находки

### 1. Оптимизация картинок была выключена целиком (исправлено)

`next.config.ts` держал `images.unoptimized: true`. Из-за этого все `sizes` в коде
не работали: аватар каста размером 48 px качал файл 800×800, постер 1600 px грузился
и в карточку каталога, и в превью 96 px. Ни WebP по запросу браузера, ни srcset.

Включили оптимизатор с узкими рамками: только WebP (AVIF кодируется в разы дольше,
а хостинг шаред), одно качество, укороченная лестница размеров, кэш на 31 день.
Удалённый доступ не открывали — `remotePatterns` пуст, оптимизировать можно только
свои же пути. Файлы из `/uploads` лежат вне public_html и отдаются Node-роутом;
оптимизатор дотягивается до них через внутренний обработчик Next, без сетевого
запроса к самому себе — то есть Passenger и его `0.0.0.0` тут ни при чём.

С трёх публичных компонентов (`cast-carousel`, `sponsors`, `product-placements`)
снят проп `unoptimized`. В админке он оставлен намеренно: трафика там мало,
а лишний CPU на шаред-хостинге не нужен.

### 2. Тяжёлая статика (исправлено)

`public/kino` — 36 кадров декоративной стены на главной, 2.2 МБ. `public/hero` — 0.45 МБ.
Пережали скриптом `scripts/optimize-static-images.mjs` (sharp, ширина ≤900 px, mozjpeg q72),
имена файлов не менялись, так что ссылки не поехали.

- `public/kino`: 2200 КБ → 994 КБ (−55%)
- `public/hero`: 450 КБ → 81 КБ (−82%)

### 3. Словарь переводов уезжает в браузер целиком

`src/lib/i18n.ts` — 976 ключей × 3 языка, 218 КБ исходника. Его импортируют 47 клиентских
компонентов, поэтому в браузер на **каждой** странице едет чанк 176 КБ со всеми языками.
На `/admin/login` это 58% всего JS страницы.

Чиним срезом: на сервере считается словарь только для текущей локали и только по тем
ключам, которые реально используются в клиентских компонентах (361 статический ключ
плюс группы `report.status.*`, `translate.*`, `faq.*`, `genre.*`, `role.*`, `category.*`,
`formatCategory.*`). Формат `i18n.ts` не меняется — редактор переводов и публикация
через GitHub API продолжают работать как раньше.

### 4. Тяжёлые клиентские библиотеки

| Либа | Вес (RAW) | Где | Что делаем |
|---|---|---|---|
| i18n-словарь | 176.7 КБ | все страницы | срез по локали (п. 3) |
| framer-motion | 131 КБ | шапка → почти везде | мобильное меню через `next/dynamic` |
| @dnd-kit | ~126 КБ | формы проекта | редакторы через `next/dynamic` |
| react-easy-crop | 37.2 КБ | кроппер | грузить при открытии диалога |
| lenis | 19.9 КБ | все страницы | грузить только там, где реально включается |

Отдельно: Turbopack не склеил framer-motion — на `/catalog` и формах проекта
качается вторая копия (те же 131 КБ) поверх уже закэшированной.

### 5. Медиа

Загрузки уже сжимаются на сервере (`src/lib/images/optimize.ts`: WebP q80,
1600×900 / 800×800 / 512×512), это работает. Проблема была не в весе файла, а в том,
что он отдавался без ресайза под место показа — закрывается пунктом 1.

Видео: 9 файлов, 79.7 МБ, самый тяжёлый локально 44.5 МБ, на проде на странице проекта
лежит ролик 15 МБ. Отдаётся Range-стримингом с `preload="metadata"` — до клика
не качается. Существующие файлы владелец решил не трогать (они живут только на сервере
Hostinger и в гит не попадают); вместо этого сжимаем всё новое при загрузке.

### 6. Серверная часть — что нашли и не стали делать

- `cookies()` в `getLocale()`/`getCurrency()` форсит полный SSR на каждый запрос,
  потому что PPR не включён. Выигрыш был бы заметный (статический каркас страницы),
  но PPR в Next 16 экспериментален, и неверно расставленные границы `<Suspense>`
  ломают локаль/валюту/сессию. Отложено осознанно.
- Строка `User` читается из БД трижды за один рендер `/reports/[id]` для роли BRAND
  (`require.ts:60`, `site-header-user.ts:15`, `reports/[id]/page.tsx:102`), плюс
  безусловный `ownsThis`-запрос для любого авторизованного. Пул Prisma ограничен
  двумя соединениями, так что лишние round-trip'ы реально сериализуют рендер.
  Фикс дешёвый и безопасный, но в этот батч не входил.
- Нет индексов под горячий фильтр `Project(isActive, moderationStatus)` + `sortOrder`,
  под `Interest.status`, `User.role`/`User.status`. При нынешнем размере таблиц
  незаметно, но дешевле добавить заранее.
- `opengraph-image.tsx` рендерит Satori и читает шрифты с диска на каждый запрос
  превью, без `revalidate`.

### 7. Решения владельца

- Кэш-заголовки для `public/` — **не делаем** (файлы будут перекачиваться каждый визит).
- Существующие видео на проде — **не трогаем**, сжимаем только новые загрузки.
- Полный вынос переводов на сервер (вместо среза) — **не делаем**, слишком широкий рефактор.
- Разбор всех 96 клиентских компонентов — **не делаем**, ограничились ленивой загрузкой тяжёлого.

## Что нашли в собственной работе

Три дефекта в срезе словаря были пойманы на проверке, до деплоя. Стоит записать,
потому что все три — типовые:

1. **Гонка между запросами.** Первая версия держала активный словарь в переменной
   модуля, а на сервере модуль один на все запросы: провайдер ставит словарь во
   время рендера, рендер прерывается на `await`, соседний запрос перетирает.
   Посетителю с `hy` уезжает `ru`, плавающе и только под нагрузкой. Лечится
   React-контекстом — он привязан к дереву рендера, а не к процессу.
2. **Английская админка поехала бы на язык посетителя.** Срез считался для одной
   локали, а `makeUI("en")` аргумент игнорировал. Провайдер теперь принимает
   словари по локалям и вкладывается: корневой layout даёт локаль посетителя,
   `admin/(panel)/layout.tsx` добавляет сверху `en`.
3. **Клиентский граф шире, чем файлы с `"use client"`.** Модуль без директивы,
   импортированный клиентским компонентом, тоже уезжает в браузер. Из-за этого
   сборка падала на `server-only`, а ключи футера и карточки проекта не попали в
   срез. Генератор ключей теперь обходит граф импортов, а не список директив.

Отдельно: функция локализации значений на клиенте читает контекст, а зовут её
внутри `.map()` — число хуков начинало зависеть от длины списка. Поэтому на
клиенте её нет вовсе, есть только `useLocalizer(locale)`, который читает словарь
один раз наверху компонента. Тест `i18n-client-keys.test.ts` падает, если список
ключей разошёлся с кодом.
