Баг подтверждён на **живом проде до правки** — `curl` + `grep` по SSR-HTML,
где соседние JSX-выражения React разделяет `<!-- -->`, так что дубль виден
в разметке однозначно.

### 3.1. Правило: куда класть разделитель

Два случая, и они решаются по-разному:

- **ключ используется в одном месте → пунктуация в словарь.** Так сделано у
  `card.release`, `card.availableOn`, `legal.updated`. Плюс: правит переводчик
  из `/admin/i18n`, без правки кода и без деплоя;
- **ключ переиспользуется где-то ещё без разделителя → `labelSep(locale)`.**
  Двоеточие в значении протекло бы в те, другие места.

Новый хелпер в `src/lib/i18n-base.ts` (модуль общей локальной обвязки, без
данных словаря — его можно импортировать из клиента, не таща в бандл 2400 строк):

```ts
export function labelSep(locale: Locale): string {
  return locale === "hy" ? "՝" : ":";
}
```

Реэкспортирован и из `i18n.ts` (сервер), и из `i18n-client.tsx` (клиент).

`ApplicationDialog` — клиентский компонент, который до сих пор получал только `t`;
ему добавлен проп `locale` (дефолт `DEFAULT_LOCALE`), пробрасывается из
`report-interest-context.tsx`.

Коммит `615a1df`.

### 3.2. Грабля: `t("…")` в комментарии к i18n-модулю сборщик считает ключом

Первый заход документировал `labelSep` примером вида `t("some.label")` прямо в
doc-комментарии. `scripts/gen-i18n-client-keys.mjs` сканирует `"use client"`-файлы
**и их зависимости** на литералы `t("…")` — и подобрал пример как настоящий ключ:
411 стало 412, `src/lib/i18n-client-keys.test.ts` покраснел
(«i18n-client-keys.ts is stale»). Комментарий переписан прозой, без вызова.
После этого 411 ключей, 299/299 тестов зелёные.
