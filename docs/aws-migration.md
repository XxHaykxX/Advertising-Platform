# Переезд на AWS (ECS Fargate + S3 + RDS)

Статус: **подготовка**. Прод живёт на Hostinger и продолжает жить до самого конца.

## Принцип

Не переезд, а **параллельный запуск**. AWS поднимается рядом с работающим Hostinger,
наполняется теми же данными, проверяется — и только потом на него переключается DNS.

Из этого следует три правила, которым подчинено всё остальное:

1. **Ни одно изменение в `main` не должно ломать сборку на Hostinger.** Всё, что добавляется
   ради AWS, — аддитивно и по умолчанию выключено. `output: "standalone"` включается только
   переменной `NEXT_OUTPUT`; S3-драйвер хранилища включится только переменной
   `STORAGE_DRIVER`; workflow `deploy-aws.yml` запускается только вручную.
2. **Откат — это смена DNS-записи обратно**, а не восстановление из бэкапа. Hostinger
   остаётся тёплым неделю после переключения.
3. **Скрипты миграции данных повторяемы.** Первый прогон делается заранее «вхолостую», на
   dev-базу; финальный — в момент переключения, и переносит только дельту.

## Целевая архитектура

| Слой | Сервис |
|---|---|
| Приложение | ECS Fargate, 1 задача, 0.5 vCPU / 1 GB, публичная подсеть с public IP, за ALB |
| Образы | ECR |
| База | RDS MariaDB `db.t4g.micro`, приватная подсеть, две БД (prod + dev) |
| Файлы | S3, ключи под префиксом `uploads/` |
| CDN | CloudFront: `/uploads/*` → S3 (OAC), `/*` → ALB |
| Обработка загрузок | Lambda на `s3:ObjectCreated` |
| Почта | SES через SDK |
| Секреты | SSM Parameter Store (SecureString) |
| Логи | CloudWatch Logs, retention 14 дней |

Задача сидит в **публичной** подсети с публичным IP намеренно: так она ходит в интернет
напрямую (GitHub API для редактора переводов, SES, Google AI) и **NAT Gateway не нужен** —
это $32/мес, которые пришлось бы платить, будь приложение на Lambda или App Runner.

## Что уже лежит в репозитории

| Файл | Что делает |
|---|---|
| `Dockerfile` | Многоступенчатая сборка, `node:22-bookworm-slim`. Debian, не Alpine — `binaryTargets` в `schema.prisma` пинует `debian-openssl-3.0.x` |
| `.dockerignore` | В образ не попадают `.env*`, `public/uploads`, тесты и доки |
| `next.config.ts` | `output` теперь читается из `NEXT_OUTPUT` — один конфиг на две цели сборки |
| `src/app/api/health/route.ts` | Пробы ALB. **Не** трогает базу: иначе моргание RDS выведет из строя все задачи и отвечать станет некому |
| `.github/workflows/deploy-aws.yml` | Сборка → ECR → перекатка сервиса. Пока только `workflow_dispatch` |
| `scripts/aws/migrate-db.sh` | Дамп с Hostinger → RDS, с проверкой на обрыв дампа и вычисткой `DEFINER` |
| `scripts/aws/migrate-uploads.sh` | rsync с Hostinger → локально → `aws s3 sync` |
| `scripts/aws/verify-parity.mts` | Read-only сверка двух БД по количеству строк, `max(id)` и чек-сумме содержимого — модели берутся из Prisma DMMF, не хардкодятся |
| `scripts/aws/verify-uploads-parity.mjs` | Read-only сверка локальной копии `uploads/` с бакетом: файлы только на одной стороне, расхождение размера — доказывает, что **копия** файлов полная |
| `scripts/aws/verify-media-refs.mts` | Read-only: каждый путь `/uploads/…`, на который ссылается живая строка в базе, реально лежит в хранилище (плюс список файлов-сирот) — доказывает, что полон **сайт**, не только копия. Переиспользует `collectMediaPaths`/`buildSnapshot` из `src/lib/history/snapshot.ts` и `storage()` из `src/lib/storage`, поэтому работает и на `STORAGE_DRIVER=fs`, и на `s3` без правок |
| `scripts/aws/server-timeouts.js` | `node -r` preload для рантайм-контейнера. Next сам выставляет `keepAliveTimeout` из `KEEP_ALIVE_TIMEOUT`, но не трогает `headersTimeout`/`requestTimeout` и не отдаёт наружу созданный `http.Server` — этот файл патчит `http.Server.prototype.listen`, чтобы выставить оба до старта. Без него дефолт Node на `requestTimeout` — 5 минут, короче планового ALB idle timeout (~900с), и долгая загрузка с телефона обрывалась бы раньше ALB |
| `infra/ecs-task-definition.{prod,dev}.json` | Реальные, валидные определения задачи ECS — единственный чек-лист рантайм-конфига, который можно проверить `jq`/валидатором, а не читать глазами. Пока справочные, не подключены к деплою — почему и что для этого нужно, раздел «Определение задачи ECS» ниже |

## Фазы

### Фаза 0 — инфраструктура (на стороне Adam)

Заказ по списку из `message for Adam.md`. Гейт: у нас на руках endpoint RDS, имя бакета,
домен CloudFront, ARN роли для OIDC, и SES вышел из песочницы.

### Фаза 1 — контейнер едет

Собрать образ, залить в ECR, поднять сервис ECS. Хранилище пока **в режиме `fs`** — файлы
лежат на эфемерном диске задачи и исчезают при рестарте. Это нормально: на этом шаге мы
проверяем только, что приложение вообще поднимается, ходит в RDS и отвечает 200.

Гейт: `/api/health` отвечает через ALB; главная, `/login`, `/admin/login` рендерятся;
в CloudWatch нет ошибок Prisma.

### Фаза 2 — данные

`migrate-db.sh` в dev-базу, `migrate-uploads.sh` в бакет. Прогон черновой — нужен, чтобы
поймать сюрпризы дампа заранее, а не в ночь переключения.

Гейт: количество таблиц совпало, количество объектов в S3 совпало с количеством файлов.

### Фаза 3 — хранилище на S3 ✅ код готов, S3-ветка не проверена на живом бакете

Драйвер лежит в `src/lib/storage/`: `keys.ts` (ключи и защита от выхода из корня),
`fs-driver.ts`, `s3-driver.ts`, выбор по `STORAGE_DRIVER`. По умолчанию **`fs`** — и это
намеренно не «угадать по окружению»: смысл всего плана в том, что `main` всё время
собирается под Hostinger, а драйвер, угадывающий по `NODE_ENV`, перевёл бы живой сайт при
первой же посторонней переменной.

Переведены на драйвер: `uploads-store.ts`, `uploads-fs.ts`, оба action-файла,
`api/uploads/route.ts`, `image-gen.ts`, `uploads/[...path]/route.ts`.

Заодно закрыта старая мелочь: `safeSegment` существовал в **двух** копиях, и копия в
`uploads-fs.ts` была слабее — без проверки на сегмент из одних точек, добавленной в
оригинал 30.07. Оба вызова передают литерал `"projects"`, так что дыра не эксплуатировалась;
копия теперь одна.

**S3-ветка проверена против живого MinIO** (19.08), без всякого AWS-аккаунта. MinIO говорит
на том же API, так что `docker run minio/minio` + `node scripts/aws/minio-dev.mjs` дают
настоящий бакет за минуту, и `e2e/uploads.spec.ts` проходит по нему **без единой правки**:
8 из 8, включая Range 206 и `Content-Disposition` у PDF. Объекты лежат под
`uploads/…` — ключ совпадает с путём в базе один в один, как и задумано.

Подтверждено замерами, а не рассуждением:

| Проверка | Результат |
|---|---|
| Отдача напрямую с «CDN» | `200`, `image/webp` |
| `/uploads/…` через приложение | `302` на CDN-URL |
| Range-запрос по редиректу | `206` — байтовые диапазоны обслуживает само хранилище |
| `Content-Disposition` у PDF | сохраняется, потому что лежит **на объекте**, а не в ответе |

🔴 **`next/image` в режиме `s3` не работает — подтверждено** (задача #12).
`/_next/image?url=/uploads/…` отвечает **400**: оптимизатор ходит за файлом через внутренний
обработчик Next и **редирект на CDN не отслеживает**. Это была гипотеза, теперь это факт.
**Режим `s3` на проде включать нельзя, пока не выбран один из трёх выходов** — см. #12.
Обратите внимание: сама отдача файлов при этом полностью исправна, ломается только
пережатие картинок под размер экрана.

**Решение владельца (19.08): чинить абсолютным origin, не выключать оптимизатор.**
Из трёх выходов #12 выбран тот, что отдаёт `next/image` файлы по **абсолютному** URL
(`https://cdn.igovazd.am/uploads/…`), а не по внутреннему пути `/uploads/…` — так
оптимизатор ходит прямо на CDN и не упирается в собственный редирект. Реализация в работе
у отдельного агента параллельно с этим документом; здесь фиксируется только решение и его
следствие: `next.config.ts` получит домен CDN в `images.remotePatterns`, а компоненты,
собирающие `src` из `key`/публичного пути, должны отдавать абсолютный URL в режиме `s3`
(в режиме `fs` — как раньше, относительный путь). Гейт фазы 3 («загрузка картинки, видео и
PDF … из кабинета участника») теперь неполон без картинки, прошедшей именно через
`next/image`, а не только через прямую отдачу.

### Фаза 3 — детали

Драйвер хранилища (задача #5). Ключевое решение: **вид путей в базе не меняется**. В базе
лежит `/uploads/videos/…`, ключ в S3 — `uploads/videos/…`, поведение CloudFront `/uploads/*`
смотрит в бакет. Один к одному, без переписывания origin path — и, главное, **без миграции
базы данных**.

Что при этом уходит из кода: `src/app/uploads/[...path]/route.ts` целиком и
`src/lib/http-range.ts` вместе с ним — S3 умеет Range-запросы сам.

Что переезжает в Lambda (задача #6): пережатие картинок через `sharp` и проверка
magic-байтов `%PDF-`. Второе — контроль безопасности, а не оптимизация: без него
переименованный `.html` отдавался бы с нашего origin. Отдача с `cdn.igovazd.am` снимает
первопричину, Lambda остаётся вторым слоем.

Гейт: загрузка картинки, видео и PDF из админки и из кабинета участника; воспроизведение
видео с перемоткой; скачивание PDF.

### Фаза 5 — переключение

1. Финальная дельта: `migrate-db.sh` + `migrate-uploads.sh` ещё раз
2. `verify-parity.mts` + `verify-uploads-parity.mjs` + `verify-media-refs.mts` —
   все три должны напечатать «OK» до следующего шага, иначе переключение не
   начинается (первые два — что копия полная, третий — что сайт полный: ни
   одна ссылка в базе не указывает в пустоту)
3. Заморозка правок контента на время окна (в первую очередь публикация словаря в
   `/admin/i18n` — Мариам предупреждена заранее)
4. A-запись `igovazd.am` → CloudFront, TTL уже понижен за 24 часа до этого
5. Проверка по поведению, не по записи DNS (заголовки CloudFront/ALB) + e2e-смоук
6. `deploy-aws.yml` переводится на `push: branches: [main]`, автодеплой Hostinger снимается
7. Hostinger не трогать неделю, затем выключить

В приложении нет своего режима «только чтение» — шаги 1–4 держатся короткими вместо этого:
чем меньше времени между финальной дельтой и переключением DNS, тем меньше писем,
регистраций и загрузок на живом Hostinger рискуют не попасть в перенос (они физически
останутся на Hostinger, но не на AWS — тот же принцип, что у отката в шаге 7 «Известных
граблей» ниже).

Пошаговый раннер с точными командами и критериями «хорошо/плохо» на каждый пункт —
`docs/aws-cutover.md`.

## Переменные окружения

🔴 **Ничего из этого не проверяется автоматически.** `deploy-aws.yml` только собирает
образ и катает `force-new-deployment` на УЖЕ существующее определение задачи ECS — он не
трогает env/secrets задачи ни строкой. В репозитории нет ни task-definition JSON, ни
Terraform/CDK. Единственное место, откуда берёт значения человек, руками создающий/правящий
задачу в консоли AWS, — эта таблица. Опечатка, забытая переменная или значение не в том
окружении не завалит сборку, не завалит тест и не завалит health-check (он намеренно не
трогает БД — см. «Известные грабли»): она проявится первым живым пользователем, попавшим на
нужную ветку кода, и симптом почти никогда не укажет на пропавшую переменную напрямую.

Ниже — полный чек-лист: что читает код, что при отсутствии, чем прод отличается от dev.
`.env.example` подпадает под `.env*` в `.gitignore` и в репозиторий не попадает, поэтому эта
таблица — единственное описание.

### Инлайнятся в сборку (`NEXT_PUBLIC_*`, `--build-arg` в `deploy-aws.yml`)

Значение фиксируется НАВСЕГДА в конкретном Docker-образе в момент `docker build` — рантайм-
переменная того же имени на уже собранном образе ничего не изменит.

| Переменная | Секрет | Где выставляется | Если отсутствует | Прод vs dev |
|---|---|---|---|---|
| `NEXT_PUBLIC_SITE_URL` | нет | GH Actions repo var `vars.NEXT_PUBLIC_SITE_URL` → `--build-arg` | `src/lib/site-url.ts` тихо подставляет `https://igovazd.am` — безопасно для прод, **опасно для dev**: OAuth `redirect_uri` и ссылки в письмах со сброса пароля с dev-контура молча указывают на прод-домен | **Обязан различаться** |
| `NEXT_PUBLIC_MEDIA_ORIGIN` | нет | GH Actions repo var `vars.NEXT_PUBLIC_MEDIA_ORIGIN` → `--build-arg` | `mediaUrl()` отдаёт путь как есть (ок только при `fs`). В `s3`-режиме от него ЕЩЁ зависит `images.remotePatterns` в `next.config.ts`, собираемый на этом же шаге — пусто здесь при сборке = оптимизатор `<Image>` навсегда 400-ит любую загруженную картинку в ЭТОМ образе, даже если рантайм-`CDN_BASE_URL` ниже настроен верно (см. находку #5 в отчёте) | Обязан различаться, если у dev свой CDN-домен |

### Рантайм, не секрет

Читается из окружения задачи ECS при каждом старте контейнера; можно поменять без пересборки образа.

| Переменная | Где выставляется | Если отсутствует | Прод vs dev |
|---|---|---|---|
| `STORAGE_DRIVER` | ECS task-def env | **Молча становится `fs`** — на Fargate это тихая потеря данных: файл пишется, отдаётся текущей задаче, и пропадает без следа на следующем рестарте/деплое (эфемерный диск, находка #4) | Одинаково: `s3` на обоих |
| `S3_BUCKET` | ECS task-def env | Явный `throw` на каждой операции хранилища при `STORAGE_DRIVER=s3` — громко, не молча | Один и тот же бакет на прод и dev (см. находку #7 — раздельного `S3_PREFIX` под dev никто не заводил) |
| `AWS_REGION` | ECS task-def env | Дефолт `eu-central-1` в коде совпадает с реальным регионом — не критично | Одинаково |
| `S3_PREFIX` | ECS task-def env | Дефолт `uploads` в коде — совпадает с путём в базе, менять только вместе с CloudFront | См. находку #7: без явного развода это дыра |
| `CDN_BASE_URL` | ECS task-def env | При `STORAGE_DRIVER=s3` отдаёт байты через приложение вместо редиректа на CDN — работает, но **без Range**, Safari не проигрывает видео (уже задокументировано, осознанно) | Разный CDN-домен, если у dev свой |
| `UPLOADS_DIR` | ECS task-def env | Актуально только при `fs`. Если `STORAGE_DRIVER` тоже не выставлен — деградирует в директорию рядом с cwd на эфемерном диске Fargate, усиливая находку #4 вместо явной ошибки | — |
| `ADMIN_EMAIL` | ECS task-def env | Фоллбэк на первого `SUPERADMIN` в БД, затем на SMTP-ящик — осознанно, безопасно | Может различаться |
| `POSTER_DAILY_LIMIT` | ECS task-def env | Дефолт 10/день в коде — осознанно | Не обязан |
| `MAIL_FROM` | ECS task-def env | Фоллбэк на `SMTP_USER` — осознанно | Может различаться |
| `GITHUB_SYNC_REPO` / `GITHUB_SYNC_BRANCH` | ECS task-def env | Дефолты в коде (слаг репозитория, `main`) — осознанно | `GITHUB_SYNC_BRANCH=dev` на dev, если там вообще держат токен (см. секреты ниже — лучше не держать) |
| `KEEP_ALIVE_TIMEOUT` | `ENV` в `Dockerfile` (910000мс) | Безопасный дефолт зашит | Одинаково, если у dev тот же ALB idle timeout |
| `HEADERS_TIMEOUT` / `REQUEST_TIMEOUT` | дефолты в `scripts/aws/server-timeouts.js` (60000 / 2400000мс) | Безопасные дефолты зашиты. Почему считаются по-разному — `### 🔴 Лимита по размеру нет, лимит по времени есть` ниже | Одинаково |

### Секреты (SSM Parameter Store, никогда не в `vars`/образе)

| Переменная | Где выставляется | Если отсутствует | Прод vs dev |
|---|---|---|---|
| `DATABASE_URL` | ECS task-def secrets (SSM) | 🔴 `PrismaClient` кидает `"Invalid value undefined for datasource"` на первом обращении к БД — но health-check намеренно её не трогает, так что ECS считает задачу здоровой, пока весь сайт, кроме горстки статических роутов, отдаёт 500 (находка #2) | **Обязан различаться** — своя БД и пользователь на прод и dev (список Adam-у) |
| `SESSION_SECRET` | ECS task-def secrets (SSM) | Пусто/короче 16 символов → громкий `throw` при первом входе. Но **валидное, просто ДРУГОЕ** значение не бросает ничего — молча перестают проверяться подписи всех уже выданных сессий, и это разлогинивает всех ровно в момент переключения без единой ошибки в логах, которая укажет на причину (находка #3, самая опасная из всех) | ⚠️ **Прод — переносится БЕЗ ИЗМЕНЕНИЙ с текущего значения Hostinger.** Dev — свой отдельный секрет, никогда не прод-значение |
| `GITHUB_SYNC_TOKEN` | ECS task-def secrets (SSM), **только прод** | `githubConfigured()` → `false`, кнопка «Сохранить и опубликовать» в `/admin/i18n` сама скрывается (`src/app/admin/(panel)/i18n/page.tsx:49`) — подтверждённый безопасный no-op | **Обязан отсутствовать на dev** — иначе публикация из тестового контура коммитит в `main` и катит прод |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | ECS task-def secrets (SSM) | `isGoogleConfigured()` → `false`, кнопка входа через Google скрывается — безопасный no-op | Обычно свой OAuth-клиент под dev-домен (redirect_uri у Google привязан к домену) |
| `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` | ECS task-def secrets (SSM) | Push отключается, warn в лог, не бросает — безопасный no-op | Не обязан |
| `GOOGLE_AI_API_KEY` / `GOOGLE_AI_MODEL` | ECS task-def secrets (SSM) | `TranslateError("notConfigured")` при попытке перевода — громко, но только когда фичу дёрнули, не при старте | Общий платный ключ — dev-тесты тратят прод-бюджет |
| `GOOGLE_IMAGE_API_KEY` / `GOOGLE_IMAGE_MODEL` | ECS task-def secrets (SSM) | `throw` при попытке сгенерировать постер — та же история, громко и только по фиче | Тот же платный ключ, то же соображение |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_USER` / `SMTP_PASS` / `SMTP_SECURE` | ECS task-def secrets (SSM) | `sendMail()` становится no-op, warn в лог, не бросает — безопасно. См. также предупреждение о песочнице SES ниже — само по себе заполнение этих пяти не гарантирует доставку | Значения — SES SMTP-credentials, см. «Почта: переезд на SES» ниже. Могут быть общими, если SES один аккаунт на оба контура |

⚠️ **Не путать с рантайм-конфигом:** `ADMIN_PASSWORD` в списке hPanel-переменных из
AGENTS.md — не рантайм приложения. Единственное место, где он читается, —
`prisma/seed.ts:12`, разовый скрипт заполнения БД (`npm run db:seed`), с фоллбэком на
захардкоженный `admin1234`, если переменная не задана. Прод-БД переезжает дампом
(`scripts/aws/migrate-db.sh`), не через seed, так что в обычном сценарии переключения это
не всплывает — но не стоит тратить SSM-запись на переменную, которую рантайм ECS не
читает вообще.

Не входят в этот чек-лист намеренно — не рантайм-переменные приложения, а параметры
одноразовых инструментов, которые кто-то запускает со своей машины против Hostinger/RDS/S3
напрямую: `SRC_HOST`/`SRC_DB`/`SRC_USER`/`SRC_PASS` и `DST_*` (`migrate-db.sh` — восемь
отдельных переменных, а **не** строка подключения), `SOURCE_DATABASE_URL`/`TARGET_DATABASE_URL`
(`verify-parity.mts` — вот здесь как раз строки подключения; два соседних инструмента
принимают одно и то же разными способами, и перепутать их легко),
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`S3_ENDPOINT` (только локальный MinIO,
`minio-dev.mjs`), `LOCAL_DIR`/`BUCKET` (`verify-uploads-parity.mjs`), `I18N_SHEET_CSV_URL` (архивный
импорт из Google Sheet, `i18n-import.ts`).

## Определение задачи ECS

`infra/ecs-task-definition.prod.json` / `.dev.json` — реальные, валидные ECS task-definition
документы, а не пример. Они и есть чек-лист из раздела выше, но в форме, которую можно
`jq`-проверить, а не прочитать глазами и надеяться.

**Почему `infra/`, а не `scripts/aws/`** — там лежат инструменты, которые *запускают*
(`.sh`/`.mjs`/`.mts` с `#!` или `node`/`tsx` перед ними); эти два файла не запускают, их
*регистрируют* (`aws ecs register-task-definition --cli-input-json`). Разная природа
файла — разная папка, а не смешивать декларативный конфиг с исполняемыми скриптами.

**Что в файле объясняет находки из аудита выше**, а не дублирует их: два файла (prod/dev),
не один — потому что `SESSION_SECRET`, `DATABASE_URL`, `S3_PREFIX` и `GITHUB_SYNC_TOKEN`
обязаны различаться (находки #2/#3/#7), а один общий файл с плейсхолдерами воссоздал бы ту
же дыру в новой форме. `S3_PREFIX=dev-uploads` на dev — тот самый развод бакета, о котором
уже написано Adam-у (`message for Adam.md`, CORS-правило «for the dev bucket prefix»).
`CDN_BASE_URL` на dev **сознательно не выставлен** — у CloudFront поведение `/uploads/*`
описано только на бакет с префиксом `uploads`, а не `dev-uploads`, так что рантайм-редирект
туда был бы битым; без переменной драйвер молча деградирует в отдачу байт через
приложение (без Range) — тот же безопасный фоллбэк, что уже задокументирован для прод-мисконфига
выше. `GITHUB_SYNC_TOKEN` в dev-файле просто отсутствует как ключ — это и есть правильное
состояние (находка «`GITHUB_SYNC_TOKEN` на dev не ставить»).

🔴 **`runtimePlatform.cpuArchitecture: ARM64` должен совпадать с `platforms: linux/arm64`
в `deploy-aws.yml`.** Это не два независимых места конфигурации одного факта — рассинхрон
не «подтормаживает», задача **вообще не стартует** (Fargate откажется запускать образ не
той архитектуры), с `CannotPullContainerError`/exec-format-подобной ошибкой, которая читается
как битый образ, а не как рассинхрон. В `deploy-aws.yml:68-74` уже есть точно такое же 🔴-
предупреждение с той же формулировкой у `platforms: linux/arm64` — эти два места нужно менять
только вместе.

⚠️ **14-дневный retention CloudWatch Logs, который просит `message for Adam.md`, в JSON
задачи выставить нельзя** — `logConfiguration` только называет группу логов
(`awslogs-group`), retention — свойство самой группы, а не ревизии задачи. Ставится один раз
через `aws logs put-retention-policy --log-group-name /ecs/igovazd-prod --retention-in-days
14` (и то же для `-dev`) — либо Adam-ом при провижининге, либо отдельной командой при первом
деплое. Файл задачи молча этого не сделает.

**Регистрировать в `deploy-aws.yml` или оставить справочным — не подключено, сознательно,
пока.** Причины, а не отговорка: `<ACCOUNT_ID>` в файле — не будущий плейсхолдер, а буквально
неизвестное на сегодня значение (доступ от Adam ещё не пришёл), и архитектура загрузок сейчас
меняется под ногами (задача #18 — видео уходит на прямой presigned-PUT в обход приложения,
раздел «Размер задачи и загрузка видео» это отследит, когда прилетит). Подключить регистрацию
сегодня — значит либо каждый ручной деплой валится на шаге `register-task-definition` с
буквальным `<ACCOUNT_ID>` в ARN (не «защита от тишины», а сломанный пайплайн до тех пор, пока
кто-то руками не проставит реальные ARN), либо тратить время на шаблонизацию (`jq`-рендер
image URI и account id перед регистрацией) под конфигурацию, которая всё равно поменяется на
следующей неделе.

**Рекомендация: подключить — как только закрыт Фазой 0 гейт** (RDS/бакет/CloudFront/OIDC-роль
от Adam на руках) **и** устоялась архитектура загрузок. Тогда стоимость подключения — одна
`jq`-подстановка `image`/`account_id` в шаблон плюс замена `--force-new-deployment` на
`register-task-definition` → `update-service --task-definition <family>:<revision>`, а
выигрыш закрывает находку #1 целиком: с этого момента файл в репозитории — это то, что
реально крутится, а не то, что кто-то надеется когда-то руками повторил в консоли. Ручная
правка в консоли AWS после этого не «дрейфует незаметно» — она откатывается следующим же
деплоем, что и есть желаемое поведение, но стоит явно знать: писать долгоживущий конфиг через
консоль после подключения станет бессмысленно, только через этот файл.

**Что останавливает дрейф до тех пор:** ничего технического — то же самое допущение, что и
сегодня, только теперь есть с чем свериться `diff`-ом. Практическое правило: любая ручная
правка task-definition в консоли AWS до момента подключения обязана в тот же день попасть
обратно в эти два файла, иначе `infra/` начинает врать по-новому, а не как раньше вообще
ничего не говорить.

## Почта: переезд на SES (решение владельца, 19.08)

При переключении почта переходит с текущего Hostinger SMTP на **Amazon SES** — не остаётся
на прежнем SMTP из AWS-сети. Ответ на «код или только конфиг»: **только конфиг**. Отправка
идёт через `nodemailer.createTransport({ host, port, secure, auth })` в
`src/lib/mail.ts:21-31`, где `host`/`port`/`secure`/`user`/`pass` уже читаются из
`SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` — generic SMTP, не
Hostinger-специфичный код. SES предоставляет точно такой же SMTP-интерфейс (эндпоинт вида
`email-smtp.<region>.amazonaws.com:587`, логин/пароль — отдельные SES SMTP credentials, не
IAM access key напрямую). Значит смена — это подстановка пяти новых значений в SSM
Parameter Store вместо старых, без единой правки `src/lib/mail.ts` или вызывающего кода.

⚠️ **Заявка на выход из песочницы SES и верификация домена — это отдельный шаг, который
нельзя откладывать на день переключения.** Новый аккаунт SES по умолчанию в песочнице: письма
доходят только до заранее подтверждённых адресов. Выход из песочницы — заявка в поддержку
AWS с рассмотрением не мгновенно (обычно от суток), плюс верификация домена `igovazd.am`
через DNS-записи (DKIM/SPF) — своё время на распространение. **Начинать эту заявку нужно
заранее, не в день X** — иначе к моменту переключения почта (регистрация, сброс пароля,
уведомления о модерации) на проде не будет доходить никому, кроме проверенных адресов.
Отражено как первый пункт «Заранее» в `docs/aws-cutover.md`.

## Что уже проверено на живом Docker (19.08.2026)

Образ собран и запущен локально против дев-базы MySQL. Результат: сборка проходит,
контейнер поднимается, Prisma подключается, страницы отдают 200 — `/api/health`, главная,

корневой области видимости (иначе у существующих подписчиков молча отвалился бы push).
Размер образа 624 МБ.

Две вещи, которые всплыли только при реальном запуске:

- 🔴 **Prisma не находит OpenSSL в `node:22-bookworm-slim`.** В образе нет бинарника
  `openssl`, по которому Prisma определяет версию, и он молча откатывается на движок
  `openssl-1.1.x`, которого в bookworm нет. Приложение при этом **стартует и отдаёт все
  статические страницы**, а падает на первом же запросе к базе. В `Dockerfile` теперь стоит
  `apt-get install openssl ca-certificates`. Сборка про это не предупреждает никак.
- **Сборке нужна не база, а сама переменная.** `next build` собирает page data по всем
  маршрутам, и конструктор `PrismaClient` бросает
  `Invalid value undefined for datasource "db"` на первом же импорте
  (`/api/auth/google/callback`). Но **подключения не происходит**: все маршруты этого
  приложения — `ƒ` (рендер по запросу), кроме `/icon.svg`, `/opengraph-image` и
  `/robots.txt`, которые в базу не ходят. Поэтому в `Dockerfile` стоит заглушка, а
  секрет `BUILD_DATABASE_URL` из workflow убран — реальные креды при сборке не нужны вовсе.

## Что держит нас на одной задаче ECS

Аудит кода 19.08 нашёл четыре счётчика, живущих в памяти процесса. Пока задача одна, они
ведут себя ровно как на Hostinger — Passenger тоже перезапускает процесс и тоже обнуляет их,
так что это **не регрессия**. Но каждый из них становится неверным в тот момент, когда задач
станет две, поэтому список зафиксирован здесь, а не забыт:

| Где | Что считает | Что будет при N задачах |
|---|---|---|
| `src/app/login/actions.ts:20` | попытки входа участника по IP (10 / 10 мин) | реальный предел становится 10 × N |
| `src/app/admin/actions.ts:31` | попытки входа staff (5 / 10 мин) | то же, и это вход в админку |
| `src/app/forgot/actions.ts:16` | запросы сброса пароля | то же, плюс усиление рассылки на чужой адрес |
| `src/lib/rate-limit.ts:12` | `POSTER_DAILY_LIMIT` — квота на **платный** Google Image API | потолок расходов становится LIMIT × N |

Плюс кэш: `unstable_cache` в `src/lib/data/projects.ts` и `ad-spaces.ts` живёт per-process, и
`updateTag`/`revalidateTag` после правки в админке погасит кэш только той задачи, которая
обработала запрос. Остальные будут отдавать старое до конца окна в 300 секунд.

Вывод: **вторую задачу не включать, пока не появится общее хранилище для счётчиков и кэша.**
Автоскейлинг у сервиса ECS должен быть выключен явно, а не «просто не настроен».

## Размер задачи и загрузка видео

⚠️ В `message for Adam.md` указано 0.5 vCPU / **1 GB** — этого мало на фазах 1–2. Тело
запроса при загрузке буферизуется в память целиком, а `MAX_BYTES_VIDEO` равен `null` (решение
владельца от 19.08), так что ролик с телефона в 4K положит задачу по OOM там, где на
Hostinger он проходил.

Фаза 3 снимает проблему совсем — при прямой загрузке в S3 по presigned URL приложение байтов
не видит. Но до неё на AWS загрузки будут хрупкими, поэтому задачу берём **2 GB** (разница
около $8/мес), а не 1 GB.

### 🔴 Лимита по размеру нет, лимит по времени есть

`MAX_BYTES_VIDEO = null` читается как «грузи что угодно», но это неправда, и разница вылезет
только на AWS. У Node есть `requestTimeout` — потолок на **всё время** запроса, а не на паузы
в нём. Заводское значение 300 с; на Hostinger оно не срабатывало никогда, потому что Passenger
буферизует тело POST на диск и отдаёт приложению уже целый файл — счётчик стартовал, когда
грузить было уже нечего. ALB так не делает, он стримит, поэтому на ECS этот таймер становится
первым, во что упирается медленная загрузка с телефона. Это **изменение поведения от самого
переезда**, а не старая дыра.

Next ни `requestTimeout`, ни `headersTimeout` не отдаёт (и `startServer()` не возвращает
`http.Server`, так что дотянуться снаружи не за что), поэтому их ставит preload-скрипт
`scripts/aws/server-timeouts.js`, подключённый через `node -r` в `CMD`.

Значение выбрано **от загрузки, а не от ALB**: 500 МБ при 2 Мбит/с ≈ 2000 с, берём
`REQUEST_TIMEOUT = 2_400_000` (40 минут) с запасом. Отсюда реальный потолок:

> **сколько успеет загрузиться за 40 минут.**

Клиент на связи хуже расчётной упрётся в него, и выглядеть это будет как случайный обрыв, а не
как лимит. Лечится подъёмом `REQUEST_TIMEOUT`, а не таймаута ALB — у того счётчик считает
простой и на активной загрузке не тикает вовсе. Насовсем отключать (`0`) нельзя: это
единственное, что ограничивает соединение, которое открыли и не досылают тело.
- **Откат деплоя** — перевешивание тега `:prod` в ECR, не пересборка. Команды в комментарии
  в `deploy-aws.yml`.

`e2e/uploads.spec.ts` — восемь проверок ровно того, что ставит под риск этот переезд.

не тот код, который поедет на прод. Это не баг, а разница окружений, но тест на ней падает:

```
UPLOADS_DIR=/tmp/e2e-uploads npx next dev -p 3012
```
