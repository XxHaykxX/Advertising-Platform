# Переезд на AWS (ECS Fargate + S3 + RDS)

Статус: **подготовка**. Прод живёт на Hostinger и продолжает жить до самого конца.

## Принцип

Не переезд, а **параллельный запуск**. AWS поднимается рядом с работающим Hostinger,
наполняется теми же данными, проверяется — и только потом на него переключается DNS.

Из этого следует три правила, которым подчинено всё остальное:

1. **Ни одно изменение в `main` не должно ломать сборку на Hostinger.** Всё, что добавляется
   ради AWS, — аддитивно и по умолчанию выключено. `output: "standalone"` включается только
   переменной `NEXT_OUTPUT`; S3-драйвер хранилища включится только переменной
   `STORAGE_DRIVER`; workflow `deploy-aws.yml` запускается только вручную.
2. **Откат — это смена DNS-записи обратно**, а не восстановление из бэкапа. Hostinger
   остаётся тёплым неделю после переключения.
3. **Скрипты миграции данных повторяемы.** Первый прогон делается заранее «вхолостую», на
   dev-базу; финальный — в момент переключения, и переносит только дельту.

## Целевая архитектура

| Слой | Сервис |
|---|---|
| Приложение | ECS Fargate, 1 задача, 0.5 vCPU / 1 GB, публичная подсеть с public IP, за ALB |
| Образы | ECR |
| База | RDS MariaDB `db.t4g.micro`, приватная подсеть, две БД (prod + dev) |
| Файлы | S3, ключи под префиксом `uploads/` |
| CDN | CloudFront: `/uploads/*` → S3 (OAC), `/*` → ALB |
| Обработка загрузок | Lambda на `s3:ObjectCreated` |
| Почта | SES через SDK |
| Секреты | SSM Parameter Store (SecureString) |
| Логи | CloudWatch Logs, retention 14 дней |

Задача сидит в **публичной** подсети с публичным IP намеренно: так она ходит в интернет
напрямую (GitHub API для редактора переводов, SES, Google AI) и **NAT Gateway не нужен** —
это $32/мес, которые пришлось бы платить, будь приложение на Lambda или App Runner.

## Фазы

### Фаза 0 — инфраструктура (на стороне Adam)

Заказ по списку из `message for Adam.md`. Гейт: у нас на руках endpoint RDS, имя бакета,
домен CloudFront, ARN роли для OIDC, и SES вышел из песочницы.

### Фаза 1 — контейнер едет

Собрать образ, залить в ECR, поднять сервис ECS. Хранилище пока **в режиме `fs`** — файлы
лежат на эфемерном диске задачи и исчезают при рестарте. Это нормально: на этом шаге мы
проверяем только, что приложение вообще поднимается, ходит в RDS и отвечает 200.

Гейт: `/api/health` отвечает через ALB; главная, `/login`, `/admin/login` рендерятся;
в CloudWatch нет ошибок Prisma.

### Фаза 2 — данные

`migrate-db.sh` в dev-базу, `migrate-uploads.sh` в бакет. Прогон черновой — нужен, чтобы
поймать сюрпризы дампа заранее, а не в ночь переключения.

Гейт: количество таблиц совпало, количество объектов в S3 совпало с количеством файлов.

### Фаза 3 — хранилище на S3 ✅ код готов, S3-ветка не проверена на живом бакете

Драйвер лежит в `src/lib/storage/`: `keys.ts` (ключи и защита от выхода из корня),
`fs-driver.ts`, `s3-driver.ts`, выбор по `STORAGE_DRIVER`. По умолчанию **`fs`** — и это
намеренно не «угадать по окружению»: смысл всего плана в том, что `main` всё время
собирается под Hostinger, а драйвер, угадывающий по `NODE_ENV`, перевёл бы живой сайт при
первой же посторонней переменной.

Переведены на драйвер: `uploads-store.ts`, `uploads-fs.ts`, оба action-файла,
`api/uploads/route.ts`, `image-gen.ts`, `uploads/[...path]/route.ts`.

Заодно закрыта старая мелочь: `safeSegment` существовал в **двух** копиях, и копия в
`uploads-fs.ts` была слабее — без проверки на сегмент из одних точек, добавленной в
оригинал 30.07. Оба вызова передают литерал `"projects"`, так что дыра не эксплуатировалась;
копия теперь одна.

⚠️ **S3-ветка написана, но против настоящего бакета не проверялась** — его ещё нет.
Проверено на живом контейнере только `fs`: отдача картинки, видео с Range (206 и корректный
`content-range`), `Content-Disposition: attachment` у PDF, 404 на отсутствующий файл.

⚠️ **Открытый вопрос — `next/image`** (задача #12). Сейчас оптимизатор ходит за `/uploads/**`
через внутренний обработчик Next без `remotePatterns` — именно это держит поверхность SSRF
закрытой. В режиме `s3` этот внутренний запрос упрётся в наш роут и получит 302 на CDN,
который оптимизатор, скорее всего, не отследит. Пока вопрос не решён, **режим `s3` на проде
включать нельзя.**

### Фаза 3 — детали

Драйвер хранилища (задача #5). Ключевое решение: **вид путей в базе не меняется**. В базе
лежит `/uploads/videos/…`, ключ в S3 — `uploads/videos/…`, поведение CloudFront `/uploads/*`
смотрит в бакет. Один к одному, без переписывания origin path — и, главное, **без миграции
базы данных**.

Что при этом уходит из кода: `src/app/uploads/[...path]/route.ts` целиком и
`src/lib/http-range.ts` вместе с ним — S3 умеет Range-запросы сам.

Что переезжает в Lambda (задача #6): пережатие картинок через `sharp` и проверка
magic-байтов `%PDF-`. Второе — контроль безопасности, а не оптимизация: без него
переименованный `.html` отдавался бы с нашего origin. Отдача с `cdn.igovazd.am` снимает
первопричину, Lambda остаётся вторым слоем.

Гейт: загрузка картинки, видео и PDF из админки и из кабинета участника; воспроизведение
видео с перемоткой; скачивание PDF.

### Фаза 4 — проверка (задача #8)

Прогон полного чек-листа по AWS-URL при живом Hostinger. Подробности — ниже.

### Фаза 5 — переключение

1. Финальная дельта: `migrate-db.sh` + `migrate-uploads.sh` ещё раз
2. Режим только-чтение на Hostinger на время переключения (иначе загрузка, сделанная между
   финальным синком и переключением DNS, потеряется)
3. A-запись `igovazd.am` → CloudFront
4. Смоук по списку
5. `deploy-aws.yml` переводится на `push: branches: [main]`, автодеплой Hostinger снимается
6. Hostinger не трогать неделю

## Переменные окружения

Существующие переносятся как есть, из hPanel в SSM Parameter Store: `DATABASE_URL`,
`SESSION_SECRET`, `ADMIN_PASSWORD`, `ADMIN_EMAIL`, `UPLOADS_DIR`, `NEXT_PUBLIC_SITE_URL`,
`SMTP_*`, `MAIL_FROM`, `VAPID_*`, `GITHUB_SYNC_*`, `GOOGLE_*`, `POSTER_DAILY_LIMIT`.

Добавляются пять новых. `.env.example` подпадает под `.env*` в `.gitignore` и в репозиторий
не попадает, поэтому единственное их описание — эта таблица:

| Переменная | Значение |
|---|---|
| `NEXT_OUTPUT` | `standalone` включает самодостаточную сборку. Ставит только `Dockerfile`; Hostinger собирается без неё и получает обычную раскладку под `next start` |
| `STORAGE_DRIVER` | `fs` (по умолчанию) — локальный диск под `UPLOADS_DIR`. `s3` — бакет. Пусто = `fs` |
| `S3_BUCKET` | Имя бакета. Читается только при `STORAGE_DRIVER=s3`; без него драйвер падает с явной ошибкой, а не молча |
| `AWS_REGION` | Регион, по умолчанию `eu-central-1`. Ключи доступа **не задаются** — на Fargate SDK берёт роль задачи из окружения контейнера |
| `S3_PREFIX` | Префикс ключей, по умолчанию `uploads`. Ровно он делает ключ в S3 совпадающим с путём в базе — менять только вместе с поведением CloudFront и `scripts/aws/migrate-uploads.sh` |
| `CDN_BASE_URL` | Origin отдачи, например `https://cdn.igovazd.am`. Пусто в режиме `s3` — конфигурационная ошибка: файлы будут отдаваться через приложение и **без поддержки перемотки видео** |

⚠️ **`SESSION_SECRET` не менять.** Он же подписывает куки на Hostinger; смена секрета
разлогинит всех ровно в момент переключения, и первое, что увидит владелец на новом
хостинге, — что он не может войти.

⚠️ **`GITHUB_SYNC_TOKEN` на dev не ставить** — иначе кнопка «Сохранить и опубликовать» в
`/admin/i18n` на тестовом контуре закоммитит словарь в `main` и задеплоит прод. Либо не
задавать токен вовсе (`githubConfigured()` сама спрячет кнопку), либо
`GITHUB_SYNC_BRANCH=dev`.

## Что уже проверено на живом Docker (19.08.2026)

Образ собран и запущен локально против дев-базы MySQL. Результат: сборка проходит,
контейнер поднимается, Prisma подключается, страницы отдают 200 — `/api/health`, главная,
`/login`, `/admin/login`, `/ads/outdoor`. Статика из `public/` отдаётся, включая `sw.js` в
корневой области видимости (иначе у существующих подписчиков молча отвалился бы push).
Размер образа 624 МБ.

Две вещи, которые всплыли только при реальном запуске:

- 🔴 **Prisma не находит OpenSSL в `node:22-bookworm-slim`.** В образе нет бинарника
  `openssl`, по которому Prisma определяет версию, и он молча откатывается на движок
  `openssl-1.1.x`, которого в bookworm нет. Приложение при этом **стартует и отдаёт все
  статические страницы**, а падает на первом же запросе к базе. В `Dockerfile` теперь стоит
  `apt-get install openssl ca-certificates`. Сборка про это не предупреждает никак.
- **Сборке нужна не база, а сама переменная.** `next build` собирает page data по всем
  маршрутам, и конструктор `PrismaClient` бросает
  `Invalid value undefined for datasource "db"` на первом же импорте
  (`/api/auth/google/callback`). Но **подключения не происходит**: все маршруты этого
  приложения — `ƒ` (рендер по запросу), кроме `/icon.svg`, `/opengraph-image` и
  `/robots.txt`, которые в базу не ходят. Поэтому в `Dockerfile` стоит заглушка, а
  секрет `BUILD_DATABASE_URL` из workflow убран — реальные креды при сборке не нужны вовсе.

## Известные грабли

- **`--column-statistics=0` обязателен** при дампе клиентом MySQL 8 против MariaDB. Без него
  дамп падает, но оставляет файл на ~6 КБ, который выглядит настоящим. В скрипте стоит
  проверка на `-- Dump completed`.
- **`DEFINER` в дампе** ссылается на пользователя Hostinger, которого на RDS нет. Скрипт их
  вырезает.
- **Одна задача ECS** — внутрипроцессный кэш Next при этом работает как сегодня. При
  масштабировании на две задачи он разъедется, и понадобится общий cache handler. Сейчас
  этого не строим.

## Что держит нас на одной задаче ECS

Аудит кода 19.08 нашёл четыре счётчика, живущих в памяти процесса. Пока задача одна, они
ведут себя ровно как на Hostinger — Passenger тоже перезапускает процесс и тоже обнуляет их,
так что это **не регрессия**. Но каждый из них становится неверным в тот момент, когда задач
станет две, поэтому список зафиксирован здесь, а не забыт:

| Где | Что считает | Что будет при N задачах |
|---|---|---|
| `src/app/login/actions.ts:20` | попытки входа участника по IP (10 / 10 мин) | реальный предел становится 10 × N |
| `src/app/admin/actions.ts:31` | попытки входа staff (5 / 10 мин) | то же, и это вход в админку |
| `src/app/forgot/actions.ts:16` | запросы сброса пароля | то же, плюс усиление рассылки на чужой адрес |
| `src/lib/rate-limit.ts:12` | `POSTER_DAILY_LIMIT` — квота на **платный** Google Image API | потолок расходов становится LIMIT × N |

Плюс кэш: `unstable_cache` в `src/lib/data/projects.ts` и `ad-spaces.ts` живёт per-process, и
`updateTag`/`revalidateTag` после правки в админке погасит кэш только той задачи, которая
обработала запрос. Остальные будут отдавать старое до конца окна в 300 секунд.

Вывод: **вторую задачу не включать, пока не появится общее хранилище для счётчиков и кэша.**
Автоскейлинг у сервиса ECS должен быть выключен явно, а не «просто не настроен».

## Размер задачи и загрузка видео

⚠️ В `message for Adam.md` указано 0.5 vCPU / **1 GB** — этого мало на фазах 1–2. Тело
запроса при загрузке буферизуется в память целиком, а `MAX_BYTES_VIDEO` равен `null` (решение
владельца от 19.08), так что ролик с телефона в 4K положит задачу по OOM там, где на
Hostinger он проходил.

Фаза 3 снимает проблему совсем — при прямой загрузке в S3 по presigned URL приложение байтов
не видит. Но до неё на AWS загрузки будут хрупкими, поэтому задачу берём **2 GB** (разница
около $8/мес), а не 1 GB.
- **Откат деплоя** — перевешивание тега `:prod` в ECR, не пересборка. Команды в комментарии
  в `deploy-aws.yml`.
