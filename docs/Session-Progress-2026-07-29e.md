**Статус: ЗАДЕПЛОЕНО.** Прод `4879e2e`, прод-БД мигрирована ДО push, билд Hostinger

## Почему это делалось

Ревью нашло HIGH, который батч P1–P10 закрыл только предупреждением: `Interest` был уникален
по паре `(бренд, проект)`, а отправка делала `upsert` по этой паре. Бренд, подавший заявку на
второй плейсмент того же фильма, **затирал первую заявку**: статус возвращался в «Отправлено»,
ответ создателя стирался, а слот, который держала принятая сделка, уходил обратно в продажу —
и никого об этом не уведомляли. После того как на странице появилась кнопка на каждой карточке
предложения, это стало одним кликом.

Владелец выбрал вариант «отдельная заявка на каждое предложение» (2026-07-29).

## Что изменилось

### Ключ предложения вместо пары

У `Interest` появилась колонка `offerKey`: `"P:<placementId>"` / `"T:<tierId>"` / `"-"`, если
бренд ничего не выбрал. Уникальность стала `@@unique([brandId, projectId, offerKey])`.

Составной уникум по `(tierId, placementId)` не подошёл бы: в MySQL NULL не конфликтует с NULL,
поэтому каждая заявка «без выбранного предложения» считалась бы отдельной, и один бренд мог бы
накопить их десятками на одном проекте. `"-"` — это отдельный, ровно один слот на проект.

Значение всегда вычисляется из двух id (`offerKeyOf` в `src/lib/offer-value.ts`) — той же
функцией кодируется значение кнопки на карточке, так что сторона отправки и сторона хранения
не могут разойтись. На это есть тесты (`src/lib/offer-key.test.ts`, 8 штук).

### Что из этого следует

- **Отзыв заявки** берёт одну заявку, а не все заявки бренда по этому фильму, и возвращает её
  слот, если она его держала. Кнопка в кабинете теперь получает id заявки, а не id проекта.
- **Страница проекта** знает состояние по каждому предложению: перекрашивается только та
  карточка, на которую подали («Заявка отправлена»), соседние остаются активными. Попап
  предупреждает о замене только когда выбранное предложение уже имеет заявку — переключение
  в списке на другое предложение убирает предупреждение. Текст предупреждения переписан: он
  говорил «по этому проекту», теперь — «на это предложение», и подсказывает, что для второй
  заявки надо выбрать другое предложение.
- **Входящие у создателя и в админке** уже были построчными и с названием предложения —
  правок не потребовалось, проверено вживую: две заявки одного бренда по одному проекту
  показываются отдельными строками со своими предложениями.

### Два пробела в учёте слотов

Оба — из-за того, что 2026-07-29 плейсменты стали доступны для заявок, а учёт был написан
только для пакетов:

1. **Принятие заявки на плейсмент ничего не бронировало** — `respondToInterest` смотрел только
   на `tier`. Один и тот же эксклюзивный плейсмент можно было продать двум брендам, и каждому
   сказать, что он его. Теперь бронь/освобождение работает для той сущности, которая указана в
   заявке, в той же транзакции; письмо бренду называет плейсмент, если пакета нет.
2. **Повторная заявка на принятый плейсмент** возвращала статус в «Отправлено», но слот
   оставался занятым — ёмкость не возвращалась, и строка держала бронь, которой противоречил
   её же статус. **Найдено живым QA уже после того, как остальное было зелёным.**

## QA (локально, вживую)

| Проверка | Результат |
|---|---|
| Две заявки на разные предложения одного проекта | Две отдельные строки (`-` и `P:4`) |
| Принятая сделка + заявка на третье предложение | Принятая цела: `MUTUAL`, слот держится |
| Повторная заявка на то же предложение | Обновляет её, статус → `SENT`, слот возвращён (0→1), история 3 события |
| Предупреждение в попапе | Есть на предложении с заявкой, исчезает при переключении на другое |
| Метки кнопок | Только карточка с заявкой — «Заявка отправлена», остальные без изменений |
| Отзыв заявки из кабинета | Удалилась одна, слот вернулся, две другие целы |
| Принятие заявки на плейсмент из админки | `MUTUAL`, слот забронирован, ёмкость 1→0 |
| Кабинет бренда | Три заявки по одному фильму, у каждой своё предложение |
| Входящие админки | Заявки построчно, с названием предложения |

## Перенос «Վալդակար» на прод

Локальный showcase — проект **34**, на проде тот же фильм — **id 3** (не 34).

Скопировано: текст (три языка), постер, галерея, видео, бюджет, дедлайн, 5 плейсментов с
картинками и буллетами, 4 спонсорских пакета (у прода картинок у пакетов не было вовсе),
10 этапов производства вместо 4.

**Намеренно не тронуто на проде:**
- **Каст.** На проде девять реальных людей с реальными загруженными фото. Локальный fill —
  десять демо-имён, а их фото лежат только на этой машине (`public/uploads` в `.gitignore`),
  так что копирование заменило бы настоящие имена демо-именами И дало бы десять битых картинок.
- Идентичность и жизненный цикл листинга: `code`, `ownerId`, `isActive`, `moderationStatus`,
  `sortOrder`, `viewCount`, `createdAt`.

Все картинки, на которые ссылается перенесённый контент, лежат в `public/kino` — он
закоммичен, поэтому прод их уже отдаёт (проверено: 200 на каждый файл).

Заявок на прод-проекте 3 не было, поэтому пересоздание дочерних строк ничего не оборвало —
скрипт переноса это проверял и остановился бы, если бы они были.
