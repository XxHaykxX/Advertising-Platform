# Release-notes формат (igovazd.am)

Триггер: пользователь говорит **«Дай мне информацию нового релиза»** (или похоже).
Действие: выдать changelog **на английском**, в шаблоне ниже, и сохранить его файлом
`docs/release-notes-v{X.Y}-en.md`. Коротко, ясно, по-человечески, без технического жаргона.
Сам этот документ — на русском; **английский только в самом ответе-релизе.**

**Язык: только английский (решение владельца 2026-07-30).** Армянскую версию больше не
делаем — v1.8 и v2.2 выходили на армянском, это отменено, файл `release-notes-v2.2.md` (hy)
удалён. Не предлагать «сделать ещё и на армянском».

## Шаблон вывода

```
Release v{X.Y} — {Month} {D}, {YYYY}

What's new and what's fixed on igovazd.am since v{предыдущая}.

— {Раздел} —
1. {Одно-два простых предложения: что нового / что починили и чем было плохо до.}
2. ...
```

Правила:
- Первая строка: `Release v{версия} — {дата}` (напр. `July 30, 2026`).
- Вторая строка всегда: `What's new and what's fixed on igovazd.am since v{предыдущая}.`
- Пункты сгруппированы по разделам вида `— Brand offers —`; сквозная нумерация через все разделы.
- Каждый пункт — 1–3 предложения. Хорошо работает приём «что стало + чем было плохо до»:
  человек понимает ценность правки, только если знает, что было сломано.
- Только пользовательские изменения (фичи + фиксы). БЕЗ тех-деталей (prisma, tsc, schema, postcss-версии и т.п. — писать «обновление безопасности», не имена пакетов).
- **ВКЛЮЧАТЬ ОБЯЗАТЕЛЬНО (иначе забуду):**
  - **Все Jira/QA-фиксы релиза** (тикеты IA-*, что чинили) — переформулированные для юзера, без номеров тикетов.
  - **Работу по локализации/переводам**, если была (новые языки, инструменты перевода контента) — как пользовательское улучшение «переводы точнее/полнее».
- Версию инкрементить от предыдущей.
